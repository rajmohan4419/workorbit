# Local financial import scope

All processing stays in the browser. CSV, XLS and XLSX imports support one explicitly selected worksheet and header row, unique non-empty headers, 10 MB files and 10,000 data-row positions (including rejected rows). Empty rows are skipped; physical spreadsheet row numbers are retained. Selecting another sheet does not import the other sheets. Amounts are limited to 1 trillion in magnitude per field to keep aggregation finite. Amounts stay numeric; only date fields interpret numeric Excel serials. Confirm mappings and inspect the preview before activating replacements. Failed or canceled replacements preserve the active source. Starting a real import from demo clears both synthetic sources when confirmed.

## JSON: `orbitboard-gstr2b/1`

This is OrbitBoard's normalized GSTR-2B invoice interchange schema, **not a raw GST portal JSON format**. Use `public/samples/gstr2b-v1.json` as a synthetic fixture. Root keys must be exactly `schema` and `invoices`; schema must equal `orbitboard-gstr2b/1`. `invoices` is a non-empty array of flat records. Allowed fields: `gstin`, `invoiceNumber`, `invoiceDate`, `taxableValue`, `igst`, `cgst`, `sgst`, `cess`. GSTIN, invoice number and taxable value require mapping; tax/date fields may be absent. Fields must be strings, finite numbers or null. Invalid amounts/dates become rejected rows; missing tax differs from explicit zero. JSON row references are one-based invoice array positions. Unsupported keys, sections, structures and versions reject the whole replacement. No amendments, credit/debit notes, imports, ISD or other sections are supported. No field mappings are inferred for unknown portal schemas.

## Matching and reporting

GSTR pairs compare taxable value and each mutually available IGST, CGST, SGST and cess component independently using the selected rupee tolerance. A component absent in one source requires review. Components absent in both are outside the comparison scope. Identifiers remain unchanged in output; punctuation-normalized duplicate keys in either source hold all candidates for review, without pairing. A single formatting variant on each side may match. Missing identifiers remain unmatched and require review. Rejected rows are excluded from monetary totals; every imported row is accounted for as processed, rejected or awaiting review. Matching does not determine ITC eligibility.

Bank statement CR/deposit means money in and DR/withdrawal means money out; ledger DR/receipt means money in and CR/payment means money out. Explicit type wins over a signed magnitude; unsupported/conflicting type tokens, negative separate debit/credit values and simultaneous non-zero debit and credit are rejected. With no type, signed amounts use positive=in/negative=out. Exact-reference candidates may match outside the date window; other candidates must satisfy the date window OR description similarity. Ties remain marked ambiguous. Balance agreement alone does not establish correctness.

XLSX text cells are written as literal string cells with no formula property. CSV exports use formula-injection protection. Reports contain source labels, row references, settings, rejects and review records. Financial fields and filenames must not enter telemetry or console logs.
